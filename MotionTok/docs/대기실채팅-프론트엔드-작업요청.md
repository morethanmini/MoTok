## 0. TL;DR — 프론트가 할 일 체크리스트

- [ ] 대기실 진입 시 `/topic/rooms/{roomId}/chat` **구독 추가** (기존 STOMP 연결 재사용)
- [ ] 채팅 입력창 + 발신: `/app/rooms/{roomId}/chat` · `{ text }` (500자 제한 UI)
- [ ] 수신 메시지 `type`으로 분기 렌더링: `TALK` 말풍선 / `GAME_SUGGEST` 제안 카드
- [ ] **버튼 분기**: 방장이면 "게임 선택"(기존 그대로), 비방장이면 **"게임 제안"**
- [ ] 게임 제안 발신: `/app/rooms/{roomId}/game-suggest` · `{ gameId, gameName }`
- [ ] `/user/queue/errors` 수신 처리(시그널과 공용 큐 — `path`로 구분)
- [ ] **(v0.2.16 신규)** 수신 메시지의 `chatId` 보관 — 신고 요청의 대상 식별자
- [ ] **(v0.2.16 신규)** 말풍선에 신고 진입점(꾹 누르기/우클릭/⋯ 메뉴) → `POST /api/v1/chat-reports` (§10)

새 연결·새 인증 방식은 없고, **신규 REST 호출은 신고 1개**(§10, 회원 전용)입니다.

## 1. 연결 — 새로 만들지 말 것

채팅은 **시그널링(WebRTC)에서 이미 쓰는 STOMP 연결(`/ws`)을 그대로 재사용**합니다.

| 항목 | 값 |
|---|---|
| 엔드포인트 | `ws(s)://…/ws` (STOMP) |
| 인증 | **CONNECT 프레임 헤더** `Authorization: Bearer {accessToken}` (회원·게스트 공통) |
| 주의 1 | WS 핸드셰이크의 HTTP 헤더가 아닙니다 — `client.connectHeaders`에 넣어야 서버가 읽습니다 |
| 주의 2 | refresh 토큰은 거부됩니다 — 반드시 access 토큰 |

### 1-1. 연결 수명주기 권장

- **연결 시점**: 대기실 입장(REST `POST /live-rooms/{roomId}/join` 성공) 직후. 시그널용으로 이미 연결돼 있으면 그 client에 구독만 추가.
- **구독 시점**: 연결 확립 즉시. **채팅은 이력이 없어서**(§5) 구독 전에 오간 메시지는 영원히 못 봅니다 — 구독이 늦으면 그만큼 유실.
- **재연결**: `@stomp/stompjs`의 `reconnectDelay` 기본 동작이면 충분. 재연결 성공 시 구독은 라이브러리가 자동 복원하지만 **끊겨 있던 동안의 메시지는 유실**됩니다(정상 — §5).
- **토큰 만료**: CONNECT 시점에만 검증하므로 연결 유지 중엔 영향 없음. 재연결 때는 `connectHeaders`를 **갱신된 토큰으로** 교체해야 합니다(만료 토큰이면 CONNECT 거부 → ERROR 프레임 → 연결 종료 반복).
- **퇴장 시**: 채팅 구독 해제(unsubscribe). 연결 자체는 시그널 쪽 수명주기를 따름.

## 2. 채널 계약

| 용도 | 방향 | destination | 페이로드 |
|---|---|---|---|
| 채팅 수신 | SUBSCRIBE | `/topic/rooms/{roomId}/chat` | `ChatMessage` (§3) |
| 내 에러 수신 | SUBSCRIBE | `/user/queue/errors` | `{ code, message, path }` (§6) |
| 채팅 발신 | SEND | `/app/rooms/{roomId}/chat` | `{ "text": "안녕하세요!" }` |
| 게임 제안 발신 | SEND | `/app/rooms/{roomId}/game-suggest` | `{ "gameId": 7, "gameName": "몸으로 말해요" }` |

발신 성공에 대한 별도 ACK는 없습니다 — **자기 메시지가 topic으로 돌아오는 것이 성공 확인**입니다(§5).
실패했다면 `/user/queue/errors`로 옵니다(본인에게만).

## 3. 수신 페이로드 — `type` 판별 union

일반 채팅과 게임 제안이 **같은 토픽**으로 옵니다. `type`으로 분기하세요.

```jsonc
// 일반 채팅
{ "chatId": "1700000000000-0",    // (v0.2.16 신규) 서버 발급 메시지 고유 ID — 신고 대상 지목에 사용
  "type": "TALK",
  "userId": "guest-abc",          // participantId — 회원: userId(숫자 문자열), 게스트: "guest-xxxx"
  "nickname": "성령",
  "text": "안녕하세요!",
  "gameId": null, "gameName": null,
  "sentAt": "2026-07-23T06:16:00Z" }   // ISO-8601, 서버 시각

// 게임 제안
{ "chatId": "1700000000001-0",
  "type": "GAME_SUGGEST",
  "userId": "guest-abc", "nickname": "성령",
  "text": "'몸으로 말해요' 게임을 제안했습니다.",   // 서버가 만든 폴백 문구
  "gameId": 7, "gameName": "몸으로 말해요",
  "sentAt": "2026-07-23T06:16:00Z" }
```

```ts
type ChatMessage = {
  chatId: string        // (v0.2.16) 서버(Redis Stream) 발급 ID — 신고 시 그대로 전달
  userId: string        // v0.2.13에서 string 확정 (SignalMessage와 동일 규칙)
  nickname: string
  text: string
  sentAt: string
} & (
  | { type: 'TALK';         gameId: null;   gameName: null }
  | { type: 'GAME_SUGGEST'; gameId: number; gameName: string }
)
```

- `userId`는 **내 메시지 판별**(참가자 목록의 내 participantId와 비교 → 말풍선 좌우 정렬)과 아바타 매칭에 쓰세요.
- `nickname`은 서버가 토큰에서 꺼낸 값이라 참가자 목록과 항상 일치합니다.
- 발신 페이로드에 신원을 넣을 필요도, 넣을 방법도 없습니다 — 서버가 세션에서 확정합니다(위조 불가 설계).

## 4. 게임 제안 — UI 상세 (이번 기능의 핵심)

### 4-1. 버튼 분기

대기실의 같은 버튼 자리가 역할에 따라 달라집니다.

| 역할 | 버튼 | 동작 |
|---|---|---|
| 방장 | **게임 선택** | 기존 동작 그대로 (백엔드 변경 없음) |
| 비방장 | **게임 제안** | 게임 목록 열기 → 게임 고르면 `game-suggest` 발행 |

- 방장 판별: 참가자 목록/방 정보의 `isHost` 또는 `hostUserId === 내 participantId`.
- **방장이 바뀌면(위임·퇴장) 버튼도 즉시 갱신**되어야 합니다 — 방장 변경 이벤트(`/topic/rooms/{roomId}/members`의 HostChanged) 수신 시 재평가.
- **버튼 분기는 프론트 책임입니다.** 서버는 방장 여부를 구분하지 않습니다(참가자면 누구나 발신 가능, 방장이 보내도 에러 아님). 화면에서만 숨기면 됩니다.

### 4-2. 발신 페이로드 규칙

```ts
client.publish({
  destination: `/app/rooms/${roomId}/game-suggest`,
  body: JSON.stringify({ gameId: game.id, gameName: game.name }),
})
```

- `gameName`은 **게임 카탈로그(`GET /games`)의 `name`을 그대로** 넣으세요(최대 50자). 서버는 이 문자열을 폴백 문구 조립과 브로드캐스트 에코에 씁니다.
- 게임 도메인이 백엔드 미구현이라 서버는 gameId **실존 검증을 하지 않습니다**(형식만: 양수, 이름 1~50자). 도메인 구현 후 서버 검증이 추가돼도 **프론트 계약은 안 바뀝니다.**
- **연타 방지**: 버튼에 짧은 쿨다운(예: 2~3초 disable)을 권장합니다. 서버에 별도 rate-limit이 없어 연타하면 그대로 방 전체에 도배됩니다.

### 4-3. 수신 렌더링

- `type === 'GAME_SUGGEST'` → 일반 말풍선 대신 **제안 카드** 권장: 게임 썸네일(카탈로그에서 `gameId`로 조회) + `nickname`님의 제안 + 게임명.
- 급하면 `text` 폴백 문구(`'OO' 게임을 제안했습니다.`)를 그대로 뿌려도 동작합니다.
- **방장 화면 한정**: 제안 카드에 "이 게임으로 선택" 버튼을 붙이면 UX가 좋습니다 — 클릭 시 기존 게임 선택 플로우 호출(이번 백엔드 범위 밖, 프론트 내부 연결만).

## 5. 렌더링·동작 특성 (꼭 알아야 하는 것)

- **자기 메시지도 topic으로 돌아옵니다.** 발신 시 로컬 append 금지 — 수신 기준으로만 그리세요. 전원이 같은 순서를 보고, 에코 수신이 곧 전송 성공 확인입니다. (에코가 ~2초 내 안 오면 실패로 간주하고 재시도 UI를 띄우는 정도가 적당)
- **이력 조회 없음**: (v0.2.16 정정) 서버가 채팅을 Redis에 저장하긴 하지만 **신고 증거용**이며 이력 조회 API는 없습니다. 입장 전 대화·새로고침 이전 대화는 못 보는 동작 그대로입니다. 채팅창 상단에 "입장 이후의 대화만 표시됩니다" 안내 문구를 권장합니다.
- **순서**: 같은 방 안에서는 브로커가 도착 순서대로 배달합니다. `sentAt`(서버 시각)으로 재정렬하지 말고 수신 순서대로 append가 안전합니다. 시각 표시용으로만 쓰세요(클라이언트 시계 사용 금지).
- **XSS**: `text`·`nickname`·`gameName`은 사용자 입력입니다. 반드시 텍스트 노드로만 렌더링(v-text/innerText). `v-html` 금지.
- **입력창**: 500자 제한 + 글자수 카운터로 선제 차단 권장(서버는 초과 시 에러 큐로 거부). 공백만 있는 메시지도 거부됩니다 — 발신 전 trim 체크.

## 6. 에러 처리 — `/user/queue/errors` (본인에게만 옴)

이 큐는 **시그널과 공용**입니다. 이미 구독 중이면 추가 구독하지 말고, `path`(문제를 일으킨 발신 destination)로 채팅/시그널 에러를 구분하세요.

```jsonc
{ "code": "CHAT_NOT_IN_ROOM",
  "message": "방 참가자만 채팅을 보낼 수 있습니다.",
  "path": "/app/rooms/abc123/chat" }
```

| code | 언제 | 프론트 처리 제안 |
|---|---|---|
| `COMMON_INVALID_INPUT` | 채팅: 빈/공백만/500자 초과 · 제안: gameId 없음·0 이하, gameName 빈 값·50자 초과 | 입력 UI에서 선제 차단했다면 거의 안 봄. 토스트 |
| `CHAT_NOT_IN_ROOM` | 방 참가자가 아닌데 발신(강퇴 직후 경합 등) | 방 상태 재조회 → 방 목록으로 이동 안내 |
| `ROOM_NOT_FOUND` | 방이 사라짐(전원 퇴장 등) | 방 목록으로 이동 안내 |
| `COMMON_UNAUTHORIZED` | CONNECT 없이 SEND/SUBSCRIBE (비정상 상태) | 연결 재수립 플로우 |
| `AUTH_INVALID_TOKEN` | CONNECT 토큰 불량/만료/refresh 토큰 | 토큰 재발급 후 재연결 |

CONNECT 실패(토큰 문제)는 에러 큐가 아니라 **ERROR 프레임 + 연결 종료**로 옵니다 — stompjs `onStompError` 콜백에서 처리.

## 7. 참고 구현 (stompjs)

```ts
import { Client } from '@stomp/stompjs'

// ── 연결 (시그널용으로 이미 있으면 이 부분은 스킵하고 client 재사용) ──
const client = new Client({
  brokerURL: `wss://${host}/ws`,
  connectHeaders: { Authorization: `Bearer ${accessToken}` },  // 재연결 전 갱신 필요
  reconnectDelay: 3000,
  onStompError: (frame) => { /* CONNECT 거부(토큰 문제 등) — 재발급 후 재시도 */ },
})
client.activate()

// ── 대기실 입장 후 ──
const chatSub = client.subscribe(`/topic/rooms/${roomId}/chat`, (frame) => {
  const msg: ChatMessage = JSON.parse(frame.body)
  messages.value.push(msg)                        // 수신 기준 append (자기 메시지 포함)
})
const errSub = client.subscribe('/user/queue/errors', (frame) => {  // 시그널과 공용 — 1회만 구독
  const err = JSON.parse(frame.body)
  if (err.path?.endsWith('/chat') || err.path?.endsWith('/game-suggest')) showChatError(err)
})

// ── 발신 ──
function sendChat(text: string) {
  if (!text.trim() || text.length > 500) return
  client.publish({ destination: `/app/rooms/${roomId}/chat`, body: JSON.stringify({ text }) })
}
function suggestGame(game: { id: number; name: string }) {
  client.publish({ destination: `/app/rooms/${roomId}/game-suggest`,
                   body: JSON.stringify({ gameId: game.id, gameName: game.name }) })
}

// ── 퇴장 시 ──
chatSub.unsubscribe()
```

## 8. 셀프 테스트 방법 (백엔드 로컬)

3. 한쪽에서 채팅/게임 제안 발신 → 양쪽 모두 수신되는지, 방 밖 사용자가 보내면 에러 큐로 오는지 확인
   (WebSocket이라 curl로는 확인 불가 — 브라우저 콘솔이나 통합 테스트 `ChatBroadcastIntegrationTest` 참고)

## 9. FAQ

- **Q. 왜 발신할 때 내 userId/닉네임을 안 보내나요?** — 서버가 STOMP 세션의 인증 정보에서 꺼내 덮어씁니다. 클라이언트가 보내면 위조가 가능해서 아예 받지 않는 설계입니다.
- **Q. sentAt이 브라우저 시간과 다릅니다.** — 서버 시각(UTC, ISO-8601)입니다. 표시할 때 로컬 타임존으로 변환하세요.
- **Q. 게임 중에도 채팅이 되나요?** — 현재 서버는 방 참가자면 허용합니다. 대기실 한정으로 바꿀지는 기획 확인 중(백엔드 1줄 수정으로 대응 가능) — 프론트는 화면 노출로만 제어하면 됩니다.
- **Q. 채팅 이력 API는 없나요?** — 없습니다. (v0.2.16부터 서버가 Redis에 저장하지만 신고 증거용이며, 이력 조회는 별도 이슈로 진행합니다.)

## 10. (v0.2.16 신규) 채팅 신고 — `POST /api/v1/chat-reports`

특정 채팅을 신고하는 **REST** 호출입니다. 지라 S15P11A706-132.

```ts
// 말풍선의 신고 메뉴에서
await api.post('/api/v1/chat-reports', {
  roomId,                       // 현재 방 ID
  chatId: msg.chatId,           // 신고 대상 메시지의 chatId (§3)
  reason: 'ABUSE',              // ABUSE(욕설·비방) | HATE(혐오·차별) | SEXUAL(음란·성희롱) | SPAM(도배·광고) | ETC(기타)
  detail: '심한 욕설을 반복함',  // 선택, 최대 200자 (ETC일 때 입력 유도 권장)
})
// 201 → { success, message, data: { reportId } }
```

**꼭 알아야 하는 것**

- **원문·작성자를 보내지 않습니다.** 서버가 Redis에서 직접 읽어 전후 맥락(±10)과 함께 DB에 스냅샷을 뜹니다.
  클라이언트가 저장해둔 텍스트를 보낼 방법 자체가 없습니다(조작 신고 차단 설계).
- **회원 전용**입니다. 게스트 토큰이면 403 — 게스트는 다인 방에 못 들어가므로 정상 흐름에선 발생하지 않지만,
  신고 메뉴 자체를 회원에게만 노출하면 깔끔합니다.
- **방을 나가면(방 폭파 포함) 신고할 수 없습니다.** 채팅 로그가 방과 함께 즉시 삭제됩니다(정책 확정).
  신고는 방에 있는 동안만 가능 — 신고 메뉴도 대기실 화면 안에서만 노출하세요.
- **자기 메시지는 신고 불가**(400 `CHAT_REPORT_SELF`) — 내 말풍선에는 신고 메뉴를 빼는 게 좋습니다.

| 에러 code | 상태 | 언제 | 처리 제안 |
|---|---|---|---|
| `CHAT_REPORT_SELF` | 400 | 자기 채팅 신고 | 내 말풍선엔 메뉴 미노출로 선제 차단 |
| `CHAT_REPORT_NOT_IN_ROOM` | 403 | 방 참가자가 아님 | 방 상태 재조회 |
| `ROOM_NOT_FOUND` | 404 | 방이 이미 폭파됨 | "방이 종료되어 신고할 수 없습니다" 안내 |
| `CHAT_MESSAGE_NOT_FOUND` | 404 | chatId가 만료·유실됨 | 동일 안내 |
| `CHAT_REPORT_DUPLICATE` | 409 | 같은 채팅 재신고 | "이미 신고한 메시지입니다" 토스트 |

관리자 조회·처리 화면(-133, `/api/v1/admin/chat-reports`)은 별도 작업 — 관리자 페이지 담당과 협의 예정.
