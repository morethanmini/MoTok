📋Pub/SubTTL —

presence:{userId}
구현(-57)✅HashTTL 60s
접속 상태·현재 방. 필드는 roomId(방 밖이면 필드 없음) · heartbeatAt(epoch ms — 총 접속시간 -141이 델타 계산 원천으로 승격, conntime:{userId} 참조). 오프라인 판정은 키의 부재 — 하트비트가 TTL을 갱신하지 못하면 Redis가 지우므로 오프라인 전이를 위한 별도 쓰기가 없다. POST /api/presence/heartbeat가 HSET+EXPIRE 하고, 응답의 intervalSeconds(=TTL/3=20s)로 프론트 호출 주기를 서버가 지정한다. 로그아웃은 TTL을 기다리지 않고 즉시 DEL. 방을 나오면 roomId를 HDEL 한다 — putAll만 하면 옛 방이 남아 영구히 IN_ROOM으로 보인다(-130의 password 잔존과 같은 함정). 회원 전용(게스트는 RDB 미영속이라 대상 아님).
conntime:{userId}
구현(-141)✅String 카운터TTL —
총 접속시간 미정산 버퍼(초). 하트비트마다 직전 비트와의 델타(presence TTL 60s로 clamp — 그보다 긴 공백은 오프라인 구간)를 INCRBY로 쌓고, 오프라인 전환을 감지한 스윕(60s 주기, presence 키 부재 확인)·로그아웃이 GETDEL로 걷어 RDB user_connect_times에 한 번에 더한다(write-behind — 매 비트 RDB upsert는 동접 증가 시 그대로 DB 부하). TTL 없음 — 만료는 곧 누적분 유실이고, flush 실패 시 값을 되돌려 다음 스윕이 재시도한다. 조회(공개 프로필 totalConnectSeconds)는 RDB 확정치 + 이 버퍼 합산이라 온라인 중에도 실시간으로 자란다.
(2026-07-27 반영, -57) 프레즌스 구현됨 — presence:{userId}가 전역 접속 상태를 담는다. room:{roomId}:members는 "그 방에 누가 있나"만 알려 주므로 "이 사용자가 어느 방에 있나"를 알려면 rooms:index 전수 조회가 필요했다 — 이 키가 그 역인덱스를 겸한다(친구방 입장 -98이 여기서 roomId를 읽는다).
STOMP 연결 이벤트가 아니라 HTTP 하트비트를 쓴 이유: 프론트 STOMP는 게임룸에서만 연결되므로(useRoomChat) 연결 여부로 판정하면 로비에 있는 사용자를 오프라인으로 보게 되고 ONLINE 상태를 표현할 수 없다. 참고로 방 단위 프레즌스(RoomPresenceTracker)는 아직 인메모리라 인스턴스가 2대 이상이면 갈라진다 — 이 키가 그 교체의 참고 구현이다.
