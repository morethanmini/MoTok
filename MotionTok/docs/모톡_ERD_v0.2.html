설계 포인트 — 구현 시 헷갈릴 지점

  
    
    
  1. 전적 조회(-97)는 LEADERBOARD만으로 충분. 게임별 플레이 횟수·최고 점수·순위가 전부 이 테이블(+Redis ZREVRANK)에서 나온다. GAME_SESSION_RESULT는 개별 판 기록(로그·분쟁 추적·-122)용이며 화면 필수 아님.
    2. 
    
  2. 정산 트랜잭션(-117)의 쓰기 순서. GAME_SESSION + GAME_SESSION_RESULT(회원만) + POINT_HISTORY/USER.point_balance + LEADERBOARD upsert를 한 트랜잭션으로. 이후 Redis rank:{gameId} ZADD GT. Redis 유실 시 LEADERBOARD에서 warm-up(비기능 -96).
    3. 
    
  3. 게스트 이관의 범위. 클라 로컬 기록을 가입 시 LEADERBOARD(best_score GT·play_count 가산)와 POINT_HISTORY(GUEST_MIGRATE)로만 반영. 세션이 이미 소멸했으므로 GAME_SESSION_RESULT는 만들지 않는다.
    4. 
    
  4. 제재↔계정 상태 동기화. SANCTION 생성 시 USER.status를 SUSPENDED/BANNED로 갱신, 일시정지 해제는 로그인 시점 lazy 체크(ends_at < now → ACTIVE 복구)로 처리하면 배치 불필요.
    5. 
    
  5. 탈퇴(-111). status=DELETED + deleted_at 기록, 닉네임·이메일은 deleted_1042 식 치환으로 UK 충돌 방지. LEADERBOARD는 조회 시 status 필터로 랭킹 노출 제외. 탈퇴 시 본인 확인 필수(자체 가입=비밀번호 / 소셜 전용=소셜 재인증)이며, OAUTH_ACCOUNT는 삭제한다.
    6. 
    
  6. 재가입 1주일 제한(-111)에 WITHDRAWN_ACCOUNT가 필요한 이유. 탈퇴하면 USER.email이 tombstone으로 덮여 "이 이메일이 언제 탈퇴했는지"를 알 방법이 사라지고, OAUTH_ACCOUNT도 지워져 소셜 식별자마저 남지 않는다. 그래서 판정용 식별자를 해시로만 따로 남긴다 — 동일성 비교만 하면 되므로 평문이 필요 없고, 탈퇴로 지운 개인정보를 되살려 두지 않는다. USER와 FK로 잇지 않는 이유도 같다(계정이 지워져도 판정은 남아야 함). 쿨다운이 지난 행은 판정에 걸리지 않으므로 배치로 정리 가능.
    7. 
    
  7. 소셜 닉네임 미수집(-22). provider 닉네임을 USER.nickname에 넣지 않는다(운영 정책 미검증 + 사용자가 고른 이름이 아님). 최초 소셜 로그인은 nickname=pending_*(28자 — 닉네임 상한 16자를 넘겨 선점 불가) + nickname_pending=true로 만들고, PATCH /users/me로 확정할 때 플래그를 해제한다.
    8. 
    
  8. AI 커스텀 아이템(-102). ITEM(item_type=AI_CUSTOM, creator_id=본인) 생성과 동시에 USER_ITEM 지급 + POINT_HISTORY(AI_GENERATE, 음수). 상점 목록 쿼리는 item_type=SHOP AND is_active만.
    9. 
    
  9. 1인 플레이·봇 판단은 전부 GAME 컬럼으로. 대기실 큐레이션: 현재 인원(봇 포함) ≥ min_players AND ≤ max_players AND is_active. 게스트 1인방은 min_players=1인 게임만 노출. 별도 플래그 불필요.
    10. 
    
  10. rank_no 네이밍. rank는 MySQL 8 예약어라 컬럼명으로 피했다. DDL 작성 시 유지할 것.
    11. 
  

  
⚠ 게스트 로컬 기록은 조작 가능하므로, 이관 시 게임별 최대 점수 상한 등 상식 검증을 반드시 거칠 것(결정 D4의 연장).
