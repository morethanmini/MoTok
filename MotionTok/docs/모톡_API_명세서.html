인증 — 대부분의 엔드포인트는 Authorization: Bearer <accessToken> 필요. 로그인/가입/소셜/게스트/공개 조회(게임·곡·리더보드)는 인증 불필요. 방 목록(GET /live-rooms)은 회원 전용이다. Access 만료 시 POST /auth/token/refresh로 갱신, Refresh는 Redis auth:refresh:{userId}(TTL 14d)에 저장되어 로그아웃 시 삭제=무효화.

토큰 수명과 갱신 전략 — Access 1시간 · Refresh 14일(발급마다 회전) · 게스트 토큰 12시간(Refresh 없음).
한 세션(로비→방→게임)이 30분을 쉽게 넘기는데 그동안 REST 요청이 거의 없다. 요청이 있을 때만 갱신하면 게임을 마치고 나올 때 토큰이 이미 죽어 로비로 못 돌아간다. 그래서 클라이언트는 ① 만료 5분 전 타이머로 선제 갱신하고(탭 복귀 시에도 확인), ② 요청 직전 만료가 임박했으면 먼저 갱신하며, ③ 그래도 401이면 1회만 갱신 후 재시도한다. Refresh는 회전되므로 동시 요청이 여러 번 갱신하지 않도록 단일 비행(single-flight)으로 묶어야 하고, 갱신까지 실패하면 로컬 토큰을 지운 뒤 세션 만료 안내 후 로그인 화면으로 보낸다. 게스트는 갱신 수단이 없어 토큰 자체를 길게 두고, 탭을 닫으면 sessionStorage와 함께 소멸한다.
회원가입 이메일 인증 — 가입은 3단계다. ① GET /auth/availability/email 중복 확인 → ② POST /auth/email/verify-request 6자리 코드 발송(Redis auth:email:code:{email}, TTL 5m) → ③ POST /auth/email/verify 코드 검증 후 발급된 verificationToken(TTL 5m)을 POST /auth/signup에 실어 보내면 서버가 1회 소비한다. 토큰이 없거나 만료·재사용이면 가입은 400으로 거절된다.
시각 표기 — 모든 date-time 값은 한국시간(KST, UTC+9) 기준이며 오프셋 없는 ISO 문자열이다(2026-07-30T18:40:00). 저장 시각은 앱의 기본 시간대에서 만들어지므로 앱이 Asia/Seoul로 고정돼 있고(BackendApplication), DB 연결도 같은 존으로 못 박혀 있다 — 배포 컨테이너 기본 존(UTC)을 그대로 두면 같은 컬럼에 9시간 어긋난 값이 섞인다. 클라이언트는 받은 문자열을 그대로 보여 주면 되고, 별도 시간대 변환을 하면 안 된다.

임시 닉네임 형식은 게스트 + 난수 4자리(예: 게스트4821)다. 게스트 세션은 탭(창)을 닫으면 사라진다 — 액세스 토큰과 임시 닉네임·1인방 ID를 모두 sessionStorage에 두고, 새로고침·화면 이동에는 유지되지만 창을 닫으면 브라우저가 함께 비운다. 게스트에겐 Refresh 쿠키가 없어 갱신 수단이 없고, 액세스 토큰 수명(jwt.guest-expiration-ms, 기본 30분)이 곧 "로그인 없이 이어서 쓸 수 있는 시간"이다 — 짧게 잡은 것은 회원 전환을 유도하기 위한 의도된 마찰이다(v0.2.24, 이전 12h). 만료되는 순간 클라이언트는 세션 만료 모달을 게스트 문구("게스트 시간(30분)이 만료되었어요! 로그인하고 다양한 사람들과 더 많은 게임을 즐겨보세요")로 띄우고 로그인 화면으로 보낸다 — 안내 없이 요청만 실패하지 않게.
회원에서 게스트로 내려오는 경우가 있어 이 응답은 회원 Refresh 쿠키를 삭제한다(Max-Age=0) — 안 지우면 게스트로 쓰는 동안 옛 회원 세션이 갱신으로 되살아난다.
호출 제한(v0.2.24) — 인증 없이 부를 수 있는데 호출마다 24시간짜리 1인방이 생기므로 IP 기준으로 app.rate-limit.guest-per-minute(기본 10)·guest-per-hour(기본 100)를 넘으면 429. 여러 사람이 같은 공인 IP를 쓰는 망(학원·사내망)을 감안해 한 명이 아니라 한 강의실 기준으로 잡았고, env로 올릴 수 있다. IP는 nginx가 덧붙이는 X-Forwarded-For의 마지막 항목을 쓴다 — 앞쪽은 클라이언트가 위조할 수 있다.
게스트는 한 게임이 끝날 때마다 회원가입/로그인 유도 팝업을 본다(문구: "로그인하시고 다양한 사람들과 더 다양한 게임을 함께 즐겨보세요!").

밀려난 세션의 토큰 즉시 폐기(v0.2.25) — 모든 회원 토큰(Access·Refresh)에 로그인마다 새로 발급되는 세션 ID(sid claim)가 실리고, 새 로그인은 옛 sid를 폐기 목록(auth:revoked-sid:{sid}, TTL=Access 수명+1분)에 올린다. 폐기된 토큰의 REST 요청·토큰 갱신·STOMP CONNECT는 전부 401 AUTH_SESSION_DISPLACED로 거절된다(로그아웃으로 폐기된 토큰은 일반 401). 옛 기기가 방에 있었다면 SFU(LiveKit) 미디어도 서버가 RemoveParticipant로 강제 퇴장시킨다.

Redis 장애 시 폐기 확인은 fail-open(서명 검증만으로 통과)이다.

key를 생략하거나 null이면 기본 아바타로 되돌린다 — 선택·변경·삭제를 한 엔드포인트로 처리한다. 사진을 교체하면 이전 객체는 트랜잭션 커밋 후 삭제한다(트랜잭션 안에서 지우면 롤백 시 참조 중인 객체가 이미 사라진다). 기본 프로필 아이콘으로 바꾸는 경우에도 그 전에 쓰던 업로드 사진은 함께 지운다.

기본 프로필 아이콘은 preset으로 고른다 — 업로드가 없으므로 S3를 거치지 않는다. 아이콘은 프론트엔드 정적 자산(/assets/icons/profile/{preset}.png)이고 서버는 형식만 검사한다(^\d{1,2}_[a-z]{2,16}$). 목록 전체를 서버에 복사해 두면 아이콘을 추가할 때마다 배포가 묶이는데, 없는 파일을 골라도 화면은 기본 아바타로 떨어질 뿐이라 피해가 없다. 다만 이 값은 친구 목록을 통해 다른 사용자 화면에 img src로 렌더링되므로 형식 검사가 방어선이다 — 슬래시·콜론·점이 못 들어가 경로 탈출과 외부 URL 삽입이 불가능하다.

업로드는 서버를 거치지 않는다. 서버는 "올려도 된다"는 서명만 발급하고, 실제 전송은 브라우저와 S3 사이에서 일어난다. 서버 메모리·대역폭을 쓰지 않아 대용량(음원)에도 견딘다. 로컬은 MinIO, 운영은 AWS S3를 쓰며 자바 코드는 동일하고 S3_ENDPOINT 유무로만 갈린다.

서버가 막는 세 지점 — 업로드가 서버를 안 거치므로 아래를 놓치면 대안이 없다.
① key는 서버가 만든다: 요청에 key·파일명 필드가 없다. 인증된 userId로 public/avatars/{userId}/{uuid}.{ext}를 조립한다 — 클라이언트가 정하면 public/avatars/999/x.png로 남의 아바타를 덮어쓸 수 있다. 확장자도 파일명이 아니라 contentType에서 뽑는다(파일명에는 ../가 섞일 수 있다).
② contentType·contentLength를 서명에 포함한다: 선언과 다르게 올리면 S3가 거부한다. 서버를 안 거치는데도 MIME·용량 제한이 서는 유일한 방법이다.
③ 업로드 후 소유권을 검증한다: 끝난 뒤 key를 도메인 API(예: PATCH /users/me/avatar)에 전달하면 서버가 내 prefix인지와 객체 존재 여부를 확인한다.

requiredHeaders를 그대로 실어야 한다 — 서명에 포함된 헤더를 브라우저가 그대로 보내지 않으면 S3가 SignatureDoesNotMatch로 거부한다. SDK 버전에 따라 서명 대상 헤더가 달라질 수 있으므로 프론트에 상수로 박지 않고 서버가 알려 준다.

URL 수명은 3분이다(S3_PRESIGN_TTL). 업로드 URL이 오래 살 이유가 없다.

서명에 Cache-Control: public, max-age=31536000, immutable이 포함된다 — requiredHeaders로 함께 내려가므로 브라우저가 그대로 실어 보내면 객체에 이 캐시 정책이 박힌다. key가 매 업로드마다 새 UUID라 같은 URL의 내용은 절대 바뀌지 않으므로(사진을 바꾸면 URL 자체가 바뀐다) 1년 + immutable이 안전하다. 이 헤더가 없으면 S3는 캐시 지시자 없이 응답하고 브라우저는 Last-Modified 휴리스틱으로 판단하는데, 방금 올라온 객체는 그 값이 0에 가까워 화면을 열 때마다 재검증 요청이 나간다 — 304로 끝나도 S3 요청 수는 그대로 늘어난다. 버킷 CORS의 AllowedHeaders에 이 헤더가 허용돼 있어야 preflight를 통과한다(현재 설정은 ["*"]).

실시간 API STOMP over WebSocket · WebRTC

WebSocket(STOMP over SockJS) 기반 방/대기실/게임 세션 이벤트와 WebRTC 시그널링. 방향 표기: client→server(앱이 SEND), server→clients(구독 SUBSCRIBE), server→user(개인 큐). 판정 권위·타이머는 서버(게임 세션 서버 -116), 정산은 write-behind(-117).

엔드포인트 wss://api.mottok.example/ws · STOMP 핸드셰이크 시 CONNECT 헤더에 Authorization: Bearer <JWT>

as-built 기준 client→server 19개 · server→client 12개 (v0.3.0) — client→server는 코드의 @MessageMapping 19개와 1:1이다(아래 /app/rooms/{roomId}/device는 그 19개에 없는 유령 채널이라 셈에서 뺐다). server→client 12개는 서버가 실제로 발행하는 목적지 기준 — 토픽 6개(/topic/lobby/rooms · /topic/rooms/{roomId}/members · /chat · /game · /rhythm · /guide)와 개인 큐 6개(/user/queue/presence · /whisper · /notifications · /signal · /game-guide · /errors)다. 접두어만 있는 /topic/rooms/{roomId}는 아무것도 발행되지 않아 뺐다.
