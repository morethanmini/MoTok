  4. 게스트 이관의 범위. 클라 로컬 기록을 가입 시 LEADERBOARD(best_score GT·play_count 가산)와 POINT_HISTORY(GUEST_MIGRATE)로만 반영.
    5. 
    
  5. 제재는 상태와 이력을 나눠 갖는다(구현 시 초안에서 바뀐 지점). 초안은 SANCTION 생성 시 USER.status를 SUSPENDED/BANNED로 갱신하고 로그인 시점 lazy 체크로 되돌리는 방식이었다. 구현은 기간 정지를 status에 담지 않는다 — 컬럼에 담으면 만료 때 ACTIVE로 되돌릴 주체가 반드시 필요하고(배치든 lazy 체크든), 그게 밀리거나 특정 경로를 안 타면 이미 풀렸어야 할 계정이 계속 막힌다. 그래서 "지금 정지 중인가"는 Redis auth:suspended:{userId} TTL이 갖는다 — 키가 사라지는 순간이 곧 해제라 복구 작업 자체가 없어지고, 남은 기간 조회도 TTL 한 번이다. sanction_history는 TTL이 증발한 뒤에도 남아야 하는 사실(누가 누구를 언제 왜 몇 일)만 담는 append-only 이력이고, 누적 정지 횟수도 여기서 센다. 근거 신고는 (id, 유형) 쌍으로 남긴다 — user_reports와 chat_reports는 별개 테이블이고 id가 각각 1부터 증가하므로 ref_report_id=7만으로는 어느 쪽 7번인지 알 수 없다. 두 테이블에 각각 FK를 걸지 않는 이유는 직권 제재(둘 다 null)가 있어 어느 쪽으로도 NOT NULL FK를 세울 수 없기 때문이다. USER.status는 스스로 풀리지 않는 상태(BANNED·DELETED) 전용으로 남긴다 — 영구 정지(-105)가 정확히 그 경우다. 밴은 만료가 있으면 오히려 버그이므로 TTL을 쓸 수 없고 status=BANNED가 원천이며, Redis auth:banned:{userId}(TTL 없음)는 요청마다 도는 인증 경로용 캐시다. 두 값의 유일한 전이는 관리자의 명시적 해제이고 그때 함께 지우므로 "되돌릴 주체가 필요하다"는 문제가 생기지 않는다. 밴을 걸 때 기간 정지 키를 지우는 것도 같은 이유다 — 남겨 두면 TTL 만료 시 "풀렸다"는 변화가 생기는데 실제로는 여전히 밴이다. 부과 시 Refresh 토큰·프레즌스를 지우고 방에서 빼고 웹소켓까지 끊어야 하는 이유는 Access 토큰이 서명만으로 유효해서(기본 1시간) 그것들 없이는 정지가 즉시 듣지 않기 때문이다. 경고(WARN)만 예외로 아무것도 끊지 않는다 — 접근을 막지 않는 제재이므로 당사자에게 전달되는 것이 곧 제재의 실행이고, 그래서 이 테이블에 유일한 갱신 컬럼 acknowledged_at이 있다(제재 사실이 아니라 전달 확인이라 append-only 원칙과 충돌하지 않는다). 푸시는 접속 중이 아니면 폐기되므로 확인 시각을 서버가 들고 있어야 못 본 경고를 다음 접속 때 다시 띄울 수 있다.
    6. 
    
  6. 탈퇴(-111). status=DELETED + deleted_at 기록, 닉네임·이메일은 deleted_1042 식 치환으로 UK 충돌 방지. LEADERBOARD는 조회 시 status 필터로 랭킹 노출 제외. 탈퇴 시 본인 확인 필수(자체 가입=비밀번호 / 소셜 전용=소셜 재인증)이며, OAUTH_ACCOUNT는 삭제한다.
    7. 
    
  7. 재가입 1주일 제한(-111)에 WITHDRAWN_ACCOUNT가 필요한 이유. 탈퇴하면 USER.email이 tombstone으로 덮여 "이 이메일이 언제 탈퇴했는지"를 알 방법이 사라지고, OAUTH_ACCOUNT도 지워져 소셜 식별자마저 남지 않는다. 그래서 판정용 식별자를 해시로만 따로 남긴다 — 동일성 비교만 하면 되므로 평문이 필요 없고, 탈퇴로 지운 개인정보를 되살려 두지 않는다. USER와 FK로 잇지 않는 이유도 같다(계정이 지워져도 판정은 남아야 함). 쿨다운이 지난 행은 판정에 걸리지 않으므로 배치로 정리 가능.
    8. 
    
  8. 소셜 닉네임 미수집(-22). provider 닉네임을 USER.nickname에 넣지 않는다(운영 정책 미검증 + 사용자가 고른 이름이 아님). 최초 소셜 로그인은 nickname=pending_*(28자 — 닉네임 상한 16자를 넘겨 선점 불가) + nickname_pending=true로 만들고, PATCH /users/me로 확정할 때 플래그를 해제한다.
    9. 
    
  9. AI 커스텀 아이템(-102)은 동기 생성이 아니라 비동기 잡 큐다. (v0.3) 초안은 "요청 = 생성 = 지급"이었지만, GPU 워커가 사내망 밖에서 호출될 수 없어 서버가 워커를 부르지 못한다 — 방향을 뒤집어 워커가 큐를 폴링한다. 흐름:
      
    ① POST /shop/ai-items — 포인트를 먼저 차감하고(AI_GENERATE, 음수) AI_ITEM_JOB(status=PENDING, points_charged)을 쌓은 뒤 jobId만 즉시 반환한다.
      
    ② 워커가 GET /api/internal/ai-jobs/next로 가져가며 status=PROCESSING · provider=GPU|FAL이 찍힌다(누가 만들었는지는 비용 정산·장애 추적에 필요하다).
      
    ③ 완료 시 POST /api/internal/ai-jobs/{jobId}/complete → 이미지가 스토리지에 올라가고 image_url이 job에 붙는다(ITEM이 아니라 job이 든다 — 저장 확정 전에도 프론트가 결과를 미리 봐야 하므로).
      
    ④ 프론트는 GET /shop/ai-items/{jobId}를 폴링해 상태를 확인한다.
      
    ⑤ 마음에 들면 POST /shop/ai-items/{jobId}/save — 그때서야 ITEM(item_type=AI_CUSTOM, creator_id=본인)이 생기고 USER_ITEM이 지급되며 job에 item_id가 채워진다.
      
    ⑥ 실패(POST .../fail → status=FAILED)면 points_charged > 0인 경우에 한해 POINT_HISTORY(AI_GENERATE_REFUND, 양수, ref_id=jobId)로 환불한다. 선차감이라 환불 경로가 반드시 필요하다.
      
    결제 1건당 생성은 최대 2회(최초 + 재생성 1회) — 재생성 job은 parent_job_id로 같은 결제 건임을 밝히고 추가 차감이 없다(points_charged=0). 한도는 프론트 상태가 아니라 uk_ai_item_job_parent UNIQUE가 최종 방어한다(새로고침으로 우회 가능하므로). 상점 목록 쿼리는 여전히 item_type=SHOP AND is_active만.
    10. 
    
  10. 1인 플레이·봇 판단은 전부 GAME 컬럼으로. 대기실 큐레이션: 현재 인원(봇 포함) ≥ min_players AND ≤ max_players AND is_active. 게스트 1인방은 min_players=1인 게임만 노출. 별도 플래그 불필요.
    11. 
    
  11. rank_no 네이밍. rank는 MySQL 8 예약어라 컬럼명으로 피했다. DDL 작성 시 유지할 것.
    12.
