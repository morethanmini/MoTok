# 게임 세션 복구 — API 명세 개정 초안

> 대상 명세: `모톡_API_명세서.html` v0.2.25 → **v0.2.26** 제안
> 상태: **초안 (컨펌 대기)** — §6이 정리되기 전까지 서버 구현에 들어가지 않는다.

## 배경 — 왜 필요한가

8명이 있는 방에서 방장이 시작하면, 그 순간 소켓이 끊겨 있던 3명은 `GAME_START`를 못 받는다.
5명은 게임을 하고 3명은 자기 카메라만 보고 있는데, **서버는 8명이 참여한 것으로 안다.**

원인은 둘이고 서로 독립이다.

1. **실시간은 델타만 보낸다.** 앱은 "끊겼다 붙으면 REST 스냅샷으로 공백을 메운다"를 이미 규칙으로
   정해 뒀지만(`useGlobalStomp.onStompConnected`), 실제로 쓰는 건 프레즌스와 로비뿐이다.
   **게임 채널에는 되찾을 스냅샷 자체가 없다** — 한 번 놓치면 그 판은 영영 복구되지 않는다.
2. **"방에 있음"과 "이 판에 참여함"이 같은 것으로 취급된다.** 서버는 정산 명부를
   `liveRoomRepository.findMembers(roomId)`로 잡는다(`GameSessionService` 300·437·498·551행).
   그래서 못 받은 3명이 0점으로 정산에 들어가 랭킹을 오염시키고, 498행의 조기 정산(전원 제출 시)은
   8명 기준이라 영영 성립하지 않아 5명이 다 끝내도 타이머 끝까지 기다린다.

## 해결 구조 — 4층

한 방에 다 넣지 않는다. **아래층일수록 싸고, 위층일수록 정확하다.**

| 층 | 내용 | 잡는 것 | 상태 |
|---|---|---|---|
| 0 | 연결 상태를 화면에 드러낸다 | 본인·방장이 끊김을 *인지* | 자기 상태 표시는 **구현 완료**, 참가자별 표시는 §1 |
| 1 | 시작 시 서버가 **구독 중인 사람만** roster로 확정 | 명백히 끊긴 사람 | §2 |
| 2 | 세션 스냅샷으로 되돌아온 사람을 복구 | 끊겼다 돌아온 사람 | §3 |
| 3 | `GAME_START` ack | **반열림 소켓** | §4 |

**왜 나누는가** — 서버는 이미 누가 붙어 있는지 안다(`RoomPresenceTracker.presence`). 끊기면 구독이
사라지므로 ack 왕복 없이도 판별된다. 다만 **반열림 소켓(양쪽 다 살아 있다고 믿는데 실제로는 죽은
상태)은 서버도 모른다** — 하트비트 타임아웃 전까지는 구독이 살아 있어 보인다. 그것만이 실제
왕복(ack)을 요구하고, 나머지는 훨씬 싸게 잡힌다.

### 이미 반영된 것 (명세 영향 없음)

- 게임룸 상단에 **자기** 실시간 연결 끊김 배너 + 새로고침 버튼
- 탭이 10초 넘게 숨어 있다 돌아오면 **소켓 강제 재접속**(`HIDDEN_FORCE_RECONNECT_MS`) — 반열림 창을 줄인다
- `startGame` 발행 실패 안내 + `GAME_START` 3초 무응답 안내
- 게임룸에서 `pagehide` 퇴장 통보 제거 → 새로고침으로 복귀 가능(`RoomPresenceTracker.GRACE_MS` 10초)

## §1. 참가자별 연결 상태 노출 (0층)

방장이 START를 누르기 **전에** "3명 연결 끊김"을 눈으로 볼 수 있어야 한다.
지금 문제의 절반은 *8명 중 3명이 자기가 끊긴 줄 모른다*는 것이다.

- `LiveRoomDetail.members[]`에 `connected: boolean` 추가.
  판정 근거는 `RoomPresenceTracker`가 그 방의 chat 토픽 구독을 들고 있는지.
- `/topic/rooms/{roomId}/members`의 기존 이벤트에도 같은 필드를 실어 변화를 밀어 준다.
- FE: 참가자 타일에 끊김 표시. 방장 START 버튼 옆에 "N명 연결 끊김".

> ⚠ 반열림 소켓은 여기서 `connected: true`로 보인다. 0층은 "명백한 끊김"만 보여 준다.

## §2. 시작 시 roster 확정 (1층)

`GameSessionService.start()`에서 **그 방의 chat 토픽을 지금 구독 중인 사람**만 이 판의 참가자로 잡는다.
아래가 전부 `findMembers(roomId)` 대신 이 roster를 본다.

- 정산 명부(`GAME_END.results`) · 조기 정산 기준(전원 제출 판정) · 게임④ 출제자 로테이션 순서 · 최소 인원 판정

**방장 UX는 "경고 후 진행"** — 하드 블록은 한 명이 계속 끊겨 있으면 방 전체가 못 놀게 만든다.
`GAME_START`에 `rosterUserIds`를 실어 보내면 각 클라이언트가 "N명은 이번 판에 참여하지 않아요"를
스스로 안내할 수 있다(새 이벤트 불필요).

roster가 최소 인원 미만이면 세션을 만들지 않고 방장에게 기존 에러(`GAME_NEED_MORE_PLAYERS`)를 회신한다.

> §4(ack)를 나중에 넣더라도 이 층은 그대로 남는다 — ack는 roster를 *좁히는* 단계일 뿐이다.

## §3. `GET /v1/live-rooms/{roomId}/game-session` — 진행 중 세션 스냅샷 (2층)

델타를 놓친 클라이언트가 현재 상태를 되찾는 **유일한 경로**. 재연결·새로고침 양쪽이 이 하나를 쓴다.

| | |
|---|---|
| 인증 | 🔒 방 멤버 (회원·게스트 공통) |
| 200 | 진행 중 세션이 있으면 스냅샷, 없으면 `data: null` |
| 404 | `ROOM_NOT_FOUND` |
| 403 | `GAME_NOT_IN_ROOM` — 방 멤버가 아님 |

### 응답 본문 · `GameSessionSnapshot`

**`GAME_START` 이벤트와 같은 필드 집합을 쓴다.** 클라이언트가 `applyGameEvent`를 그대로 재사용할 수
있어야 복구 경로가 별도 분기로 갈라지지 않는다 — 갈라지면 둘 중 하나는 반드시 뒤처진다.

| 필드 | 타입 | 설명 |
|---|---|---|
| `sessionId` | string | |
| `gameId` | number | |
| `challenge` | string \| null | 게임별 과제 payload (-137) |
| `constellationKey` | string \| null | 게임① 하위호환 |
| `setterUserId` | string \| null | 게임④ 출제자 |
| `difficulty` | string \| null | |
| `mode` / `wallCount` | string \| null / number \| null | 게임④ (-9) |
| `roundNo` / `totalRounds` | number \| null | 게임④ 로테이션 (-48) |
| `topicWord` / `turnOrder` / `turnDurationSec` / `handoverSec` | | 게임⑩ (v0.2.20) |
| `serverNow` | number | **조회 시점** epoch ms — 클라이언트 시계 오프셋 보정 |
| `startAt` / `endAt` | number | epoch ms |
| `finishedUserIds` | string[] | 이미 제출을 마친 참가자 — 늦게 합류한 사람이 진행 현황을 맞춘다 |
| `rosterUserIds` | string[] | 이 판의 확정 참가자 (§2) |

### 클라이언트 규약

- 게임룸 마운트 시 1회 + `onStompConnected`(**재**연결) 때마다 호출.
- `null`이면 대기실 상태를 유지한다.
- `endAt - serverNow <= 0`이면 **합류하지 않고** 결과(`GAME_END`)를 기다린다 — 남은 시간이 없는
  판에 붙여 봐야 0점 제출만 만든다.
- 내가 `rosterUserIds`에 없으면 **관전**으로 붙는다(순위에 들지 않는다).
- 그 외에는 남은 시간만큼만 플레이한다. 서버 타이머가 권위이므로 클라이언트가 시간을 늘리지 않는다.

## §4. `GAME_START` ack (3층) — 반열림 소켓 전용

§2로도 안 잡히는 잔여 케이스는 반열림뿐이다. 실제 왕복만이 드러낼 수 있다.

### `SEND /app/rooms/{roomId}/game/ack` · client→server

본문: `{ "sessionId": "..." }` — `GAME_START`를 **받은** 클라이언트가 즉시 보낸다.

- 서버는 카운트다운(`games.countdown_sec`) 종료 시각(= `startAt`)에 roster에서 **ack 없는 사람을 뺀다.**
  카운트다운은 원래 "곧 시작한다"를 보여주는 구간이라 그대로 ack 창으로 쓴다(대기 시간 추가 없음).
- `startAt` 이후 도착한 ack는 무시한다.
- 좁힌 결과가 최소 인원 미만이면 세션 취소가 필요하다 → §6-3 참고.

### 호환성 ⚠

ack를 보내지 않는 구버전 클라이언트는 roster에서 빠져 게임이 성립하지 않는다.
**FE·BE 동시 배포가 전제다.** §2가 먼저 들어가 있으면 ack 미지원 클라이언트도 최소한
"구독 중"으로는 잡히므로, 단계 배포 폴백을 §2에 맡길 수 있다.

## §6. 컨펌이 필요한 열린 질문

1. **§1의 `connected` 판정을 어디에 실을지.** 방 상세에만 둘지, members 토픽에도 밀지.
   토픽에 밀면 실시간이지만 끊김/복구가 잦을 때 이벤트가 늘어난다.
2. **§2에서 roster가 방 멤버보다 적을 때 방장을 막을지.** 초안은 "경고 후 진행".
3. **roster < 최소 인원일 때.** §2는 기존 `GAME_NEED_MORE_PLAYERS`로 시작을 거부하면 되지만,
   §4에서 *이미 시작한 뒤* ack로 좁혀져 미달이 되는 경우는 취소 이벤트가 필요하다 —
   `GAME_ABORTED`를 신설할지, 빈 `results`의 `GAME_END`로 대신할지(후자는 "취소"와 "전원 0점"이 구분되지 않는다).
4. **§3으로 돌아온 사람을 roster에 넣을지.** 초안은 "안 넣는다"(관전 가능, 순위 제외).
   `startAt` 이전 복귀면 편입하는 안도 가능하다.
5. **§4를 지금 할지.** §1~§3만으로 명백한 끊김은 모두 덮인다. 반열림은 이미
   `HIDDEN_FORCE_RECONNECT_MS`(탭 복귀 시 강제 재접속)로 창이 줄었으므로, 실측 후 결정하는 안도 있다.
